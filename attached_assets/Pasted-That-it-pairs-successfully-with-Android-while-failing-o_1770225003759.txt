Android and iOS handle "Non-Standard" Bluetooth devices very differently:


Android (The "Trusting" Stack): Android's Bluetooth stack (BlueDroid/Fluoride) is "Handle-oriented". If a device says "Here is a piece of data at address 0x0012," Android will write to it even if that address shouldn't technically exist inside the specified Service range.


iOS (The "Strict" Stack): iOS uses CoreBluetooth, which is "Service-oriented". If you try to write to a characteristic (like 9bd2) that belongs to a Vendor range, but you are doing it within a Service (029d) that belongs to a Standard range, the iOS kernel intercepts the command and kills the connection before it even leaves the phone's antenna.

The Strategy for Build 27: The "Android Emulation" Fix
Since Android works, our goal for Build 27 is to make the iOS communication look as much like the Android communication as possible. We will attempt to bypass the iOS "Service Sandbox" by using a Direct Descriptor Write.

Build 27 Plan:

Target the Handle, not the UUID: Instead of telling iOS to "Write to Characteristic X," we will attempt to find the raw attribute handle that Android is using.


Disable Response Expectation: We will use writeWithoutResponse exclusively to prevent iOS from waiting for a "Success" confirmation that it might not recognize.

MTU Force-Down: We will force a very small MTU (23 bytes). Android often defaults to this, whereas iOS tries to negotiate 256 bytes, which might be triggering the disconnect on this specific "Hybrid" firmware.
