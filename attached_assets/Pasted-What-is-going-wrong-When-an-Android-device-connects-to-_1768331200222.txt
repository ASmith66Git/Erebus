What is going wrong?
When an Android device connects to a Shearwater (which uses a Serial-over-BLE profile), it expects to see a specific Service UUID (usually 0xFEBA or a proprietary Shearwater UUID) and its associated characteristics.

In your case, the Android BLE stack is returning an empty list of services. This is a common "ghosting" issue on Android where the phone caches a previous (incorrect) version of the device's service table.

Why "Operation cancelled (error code 2)"?
This error is being thrown by your React Native BLE library (likely react-native-ble-plx).

The Cause: Your code is likely calling discoverAllServicesAndCharacteristics() or attempting to write to a characteristic.

The Result: Because the initial service discovery failed (or returned nothing), the internal promise is rejected because the "target" for the command simply isn't there in the phone's memory.

Recommended Fixes
1. Clear the GATT Cache
Since the log specifically mentions "clearing GATT cache," ensure you are actually performing a physical reset.

On the Dive Computer: Turn Bluetooth off and back on.

On the Android Device: Toggle Airplane mode or, better yet, go to Settings > Apps > See all > Bluetooth > Storage & Cache > Clear Cache.

2. Check Android 15 (API 35) Permissions
You are running Android version 35 (Android 15). This version has very strict requirements for Bluetooth permissions. Ensure your AndroidManifest.xml and runtime requests include:

BLUETOOTH_SCAN (with neverForLocation if applicable)

BLUETOOTH_CONNECT

ACCESS_FINE_LOCATION (Still required for service discovery on many implementations)

3. Implement a Delay before Discovery
Shearwater devices sometimes take a moment to "wake up" the serial service after the initial connection.

Code Change: Add a 2-second delay between the device.connect() call and the device.discoverAllServicesAndCharacteristics() call. Android's GATT stack often fails if you spam discovery requests immediately after the connection event.

4. Validate the Service UUID
If you are using a filter to find the Shearwater service, it might be failing because the UUID has changed or is being masked. Try to list all services discovered and log their UUIDs to see if the Shearwater service is showing up under a different ID than libdivecomputer expects.
